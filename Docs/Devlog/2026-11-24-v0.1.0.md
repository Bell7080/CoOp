# v0.1.0 개발 로그 — 2026-11-24

## 목표

두 개발자가 Codex·Claude와 함께 Windows용 협동 공포 게임을 개발한다. 최소 권장 2인, 최대 6인이다. 지금은 방장 PC를 리슨 서버로 사용하는 인터넷 테스트 환경을 구성하고, 이후 Steam 연결과 근접·무전 음성을 붙일 수 있도록 분리한다.

## 구성

- 프로젝트: `D:\Unity Games\CoOpHorror`.
- 에디터: Unity 6.3 LTS `6000.3.29f1`. 기존 에디터 유지. 드라이브 이동은 사용자가 취소하여 수행하지 않았다.
- 그래픽: Universal 3D, URP 17.3.0. 게임의 최종 아트/조명은 아직 결정하지 않았다.
- 개발 접속: MPS Sessions + Relay. 방장 PC에서 NGO 서버/클라이언트를 함께 실행한다. 중계 서버가 게임 시뮬레이션을 대신하지 않는다.
- 저장소: `https://github.com/Bell7080/CoOp`. 기존 README/.gitignore 이력 보존 후 로컬 프로젝트를 연결했다.
- 버전: 0.1.0부터 기록. 1.0.0은 정식 출시 승인 전 사용 금지.

## 구현

`IRoomGateway`는 방 연결의 경계다. `RelayRoomGateway`가 개발용 인터넷 방을 생성/참가한다. `RoomController`가 단일 작업 처리, 접속 승인, 서버 지정 스폰 위치, 퇴장과 오류 표시를 관리한다. NGO 프리팹은 `ConnectionAvatar`이며 서버만 기록하는 신호 값을 동기화한다.

Steam으로 바꿀 때에는 실제 호환되는 NGO 전송 계층과 방 연결 구현을 추가해야 한다. 단순 설정 하나로 Steam 전송으로 바뀌는 상태라고 주장하지 않는다.

## 검증과 관찰

2026-11-24, 동일 PC의 **별도 MPPM 프로세스** 두 개로 Relay 경유 테스트를 했다. 실제 두 집의 PC 테스트를 대신한다고 주장하지 않는다.

| 검사 | 관찰한 결과 |
|---|---|
| 방 생성 | `host: true`, `clients: 1` |
| 별도 프로세스 참가 | `connected: true`, `clientId: 1`, `transport: UnityTransport` |
| 호스트의 접속 목록 | `connectedClientIds: [0,1]`, `objects: 2` |
| 클라이언트→서버→클라이언트 상태 | 양쪽 `ConfirmedSignals: 1` |
| 참가자 퇴장 | 호스트에 `clients: 1`, `objects: 1` |
| 재참가/늦은 초기 동기화 | `id: 2`, host `signals: 1` 수신 |
| 방장 종료 | 클라이언트 `connected: false`, 종료 안내 표시 |
| 인원 제한 승인 콜백 | `[true,true,true,true,true,true,false]` |
| 빌드 불일치 | `mismatchedBuildRejected: true` |
| 클라이언트 런타임 콘솔 | 오류 0, 경고 0 |

실패/조정한 확인 시도도 기록한다.

- 패키지 설치 후 도메인 재로드 도중 호출한 CLI 명령은 잠시 `EDITOR_NOT_RUNNING`이었다. 재컴파일 완료 후 정상 연결됐다.
- MPPM 시작 직후 아직 Play 모드 전인 상태에서 `RoomController.Instance`를 읽어 NullReference가 났다. 모든 플레이어가 실제 playing 상태가 된 뒤 호출했다.
- 클라이언트에서 `GetPlayerNetworkObject(0)`로 원격 호스트 객체를 읽는 확인 코드가 null을 반환했다. 실제 생성된 NetworkObject/ConnectionAvatar에서 소유자 ID를 찾아 기존 신호와 이동을 검증했다. 확인용 조회 코드의 실패였으며, 사용자 게임 코드에 이 조회를 넣지 않았다. 세션 접속 완료와 객체 조회 가능 시점을 구분한다.
- 현재 패키지 조합에는 문서의 `netcode.gameobjects` CLI 그룹이 없어 동일 상태를 NGO API와 `script eval`로 직접 확인했다.

## 남은 작업

- 친구 PC에서 방 생성/코드 참가/양방향 이동/종료 테스트.
- Steam 네트워킹, 실제 마이크, 근접·무전 음성, 자동 호스트 이전은 미구현.
- 기본 캡슐은 개발용 연결 샌드박스이며 완성된 공포 게임 플레이 루프가 아니다.

## 최종 0.1.0 확인

- `VERSION`, `PlayerSettings.bundleVersion`, 실행 중인 양쪽 `Application.version` = **0.1.0**.
- 클라이언트 이동 `(0, 1.05, 2)`을 호스트가 동일하게 수신했다.
- 호스트 이동 `x=-0.9999996`을 클라이언트가 동일하게 수신했다.
- 클라이언트에 Multiplayer Tools Network Simulator를 임시 추가해 100ms 지연, 20ms 지터, 2% 손실을 적용했다. `IsAvailable=true`, 연결 유지, 양쪽 신호 값 2를 확인했다. 시뮬레이터는 Play 모드 테스트 객체로만 사용하고 저장된 씬에는 남기지 않았다.
- 서버 신호 RPC에 소유자 제한을 명시한 최종 코드로 검증했다.
- Windows x64 개발 빌드 성공: `Builds/WindowsDev/CoOpHorror.exe`. 약 171초가 걸렸다. 실제 친구 PC에서 실행한 검증은 아직 아니다.
- 별도 시험 폴더에서 버전 명령을 실제 실행해 `0.1.0 → 0.1.1 → 0.2.0`, README·CHANGELOG·개발 로그의 동시 갱신, 문자 그대로의 `$1` 처리, 1.0.0 입력 거절을 검증했다. 게임 프로젝트 자체는 초기 버전 **0.1.0**을 유지했다.
- 방과 참가자를 명시적으로 퇴장시키고 MPPM 시나리오를 중지했다.
- Windows 개발 빌드를 숨김 프로세스로 약 8초 실행해 시작 씬과 스크립트가 로드되는지 확인했다. 주요 예외/씬·어셈블리 로딩 실패 검사 결과 0건이었다. 마이크·두 실제 PC 접속 검증은 아니다.
- 마지막 검사에서 NGO `RequireOwnership`의 폐기 경고를 발견해 설치된 2.14의 `InvokePermission = RpcInvokePermission.Owner`로 수정했다. 수정 뒤 재컴파일 오류·경고는 0개다.
- 마지막 API 변경 뒤 다시 별도 프로세스로 Relay 참가·신호·이동을 검증했다. 참가자 `signal=1`, `z=0.2`에 대해 호스트가 `signal=1`, 보간 중 `z=0.195007533`을 수신해 허용 오차 안에서 통과했다. 이후 최종 Windows 빌드도 다시 생성했다.
